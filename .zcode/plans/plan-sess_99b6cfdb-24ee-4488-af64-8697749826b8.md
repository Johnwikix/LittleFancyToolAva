## 目标
允许用户在不破坏现有"白名单 + 完整预览"的前提下，选择扩展名不在 15 项白名单内的 H.265 裸流等二进制文件进入转码列表。

## 设计原则
- **FFmpeg 自己会嗅探内容**：真正转码时调用的是 `ffmpeg.avformat_open_input(&ifmtCtx, inputPath, null, null)`，依赖 FFmpeg 内置 probe。只要 FFmpeg 能解析就一定能转。**当前所有限制都在 UI 入口层**（FilePicker 过滤器、运行时 `VideoExtensions.Contains` 二次拦截、拖放 CanAccept 拒绝）。
- **不重构白名单为接口**：保留现有 15 项 + 三处硬编码的现状（白名单继续保留以避免误选无关文件），只**新增一条"All Files"入口**并**放宽运行时拦截**。
- **改动面尽量小**：聚焦 4 处行为变化 + 1 个 UI 开关 + 3 条 i18n 文案。

## 改动清单

### 1. `FancyTool/ViewModels/VideoTranscodeViewModel.cs`
- 第 19-22 行的 `VideoExtensions` HashSet：保留不动。
- 第 725 行的 FilePicker 过滤器：从 11 项扩到完整 15 项（补 `.3gp / .ts / .mts / .m2ts`），并追加一个 `*.*` 的"所有文件"过滤项，使 OS 对话框同时显示两类。
- 第 731 行的 `AddFiles` 运行时检查：从 `VideoExtensions.Contains(...)` 改为"扩展名为空 ∪ 命中白名单"都允许（即去掉拦截）。这样用户在对话框选了无扩展名/非常规扩展名文件也能加入列表。
- 第 742-759 行的 `AddFolder`：增加 `bool includeAll` 参数（由 UI 开关传入），默认 false 时仍按白名单过滤，true 时不再过滤。

## 不做的事
- **不**输出容器映射逻辑（FFmpeg 探测后由现有 UI 的"输出格式"下拉框控制容器，与你的回答一致）。
- **不**改动 `VideoTranscodeService.cs` 任何转码逻辑（它本来就是 `avformat_open_input` 自动嗅探的，UI 放行即可生效）。
- **不**引入新的接口 / 抽象层（如 `IInputFormatPolicy`），保持小改动。
- **不**重构拖放 View 与 VM 中两份重复 HashSet（合并为 VM `internal static`，但不动更深的架构）。

## 验证步骤（实施时）
1. 在 VM 注入 `INotificationService`（已注入，见第 27 行）。
2. 跑 `dotnet build` 确认编译通过。
3. 人工验证：
   - FilePicker 同时显示"视频文件"和"所有文件"两类。
   - 选择无扩展名文件（如 `h265_raw.bin`）能被加入列表。
   - 选择白名单外文件能加入列表，加入后 ProbeInfo 立刻显示流信息或弹"无法识别"提示。
   - 拖放无扩展名文件成功；勾选"包含所有文件"开关后扫描文件夹能收所有文件。
   - 状态保持：开关位在重启后恢复。
4. 错误路径：选一个完全无关的文件（如 .txt），FFmpeg 探测失败 → 弹 warn 但仍允许留在列表（避免误清空；如果你希望失败时自动移出，再讨论）。
